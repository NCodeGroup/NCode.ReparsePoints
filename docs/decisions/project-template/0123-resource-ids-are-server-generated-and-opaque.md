# 0123. Resource identifiers are server-generated and opaque

- **Status:** Accepted
- **Date:** 2026-10-31

## Context

This decision applies to projects that host ASP.NET Core and expose addressable resources over an API.

An API that creates resources must decide who chooses each resource's identifier, and what shape it has. Two facts
shape the answer:

- An identifier's guessability is not a security control. Every resource is behind an authorization check; if an
  unguessable id were load-bearing, the authorization would be the bug.
- The database usually has its own surrogate primary key. The identifier exposed on the wire is a second identifier,
  so how it is minted touches only the create path, not the schema.

A caller-chosen identifier welds "what someone typed once" to "what every foreign key, reference, and log record
points at", so it can never be renamed, and it pushes format, validation, and collision handling onto every caller.

## Decision

Every resource identifier exposed by the API is generated by the server and is opaque.

- A create request does not carry the identifier of the resource it creates. The server mints it and returns it in the
  `201 Created` body and the `Location` header.
- The identifier is a 128-bit value from a cryptographically secure generator, base64url-encoded, with no prefix or
  structure: `Base64Url.EncodeToString(RandomNumberGenerator.GetBytes(16))`. It is produced behind one injectable
  generator, so tests can control it.
- Internal surrogate keys (database identities, sequential or time-ordered keys) are never exposed.
- Names stay names. Human-meaningful, caller-supplied fields (a display name, a slug used for lookup) are ordinary
  mutable properties beside the identifier.
- A reference to an existing resource (the parent a new resource attaches to) stays caller-supplied.
- Uniqueness is still enforced by a unique constraint, as a cheap safety net, although a collision at 128 bits is
  astronomically unlikely.

## Options considered

- Caller-supplied natural keys. Rejected as the default, for the coupling described above. It remains defensible for an
  identifier a client must know before the resource exists, as an explicit, separately reviewed option.
- `Guid.NewGuid()`. Rejected: about 122 random bits, and not contractually generated by a secure generator.
- Time-ordered identifiers (snowflake, UUIDv7, ULID). Rejected for exposed identifiers: they leak creation time and
  ordering. They remain a good choice for internal surrogate keys.
- Type-prefixed identifiers (`ord_...`). Rejected: a parsing surface with no benefit unless the project needs
  self-describing ids, in which case it records that choice separately.
- Opaque random string (chosen). The simplest identifier that is unguessable, unpredictable, and pattern-free.

## Consequences

- Create requests carry content and parent references only; callers read the new identifier from the `201` response.
- Renaming a resource never disturbs its identifier, its foreign keys, or references held elsewhere.
- Identifiers carry no meaning, so nothing (sort order, creation time, ownership) may be inferred from them; ordering
  uses an explicit column.
