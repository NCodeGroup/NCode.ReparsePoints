# 0146. Secrets are never logged, are compared in constant time, and are shown once

- **Status:** Accepted
- **Date:** 2026-10-31

## Context

A secret leaks most often through the application's own diagnostics, not through an attack on its storage. A token
logged at Debug "just for now", a request payload stored with its `Authorization` header, an exception message that
quotes the connection string, an audit event that records the API key it validated: each copies the secret into a
system with wider access and longer retention than the store that protects it.

Comparison leaks too. `==` on strings, `SequenceEqual` and `string.Equals` return at the first byte that differs, so
the time a comparison takes reveals how much of a guess was right, and a secret, MAC or verifier can be recovered a
byte at a time.

A credential the application generates (an API key, a client secret, a webhook signing key) has a third failure: an
endpoint that returns it on every read makes every read, cache, log line and browser history a copy of it, and a
credential stored as plain text is exposed by any backup.

## Decision

A secret appears in exactly one response, is stored only in a form that cannot be read back, and never reaches a
diagnostic sink; secrets and their derivatives are compared in constant time.

1. What counts. A secret is a password, token, API key, client secret, private or symmetric key, signing or
   encryption key material, a connection string with credentials, a session handle or cookie value, an
   `Authorization` header, a one-time code, or a verifier.
2. Never in diagnostics. A secret never reaches a log entry, a span attribute, a metric, an audit or domain event, an
   exception message, a `ToString` result, a problem details body, or a stored copy of a request. Logs and events carry
   identifiers and metadata: which key, not the key. A request logged or stored for later has its credentials removed
   first, logs the path rather than the query string, which can carry codes and tokens, and logs headers from an
   allow-list, never all of them.
3. Constant-time comparison. A secret, MAC, hash or verifier is compared with
   `CryptographicOperations.FixedTimeEquals` over bytes, never `==`, `SequenceEqual` or `string.Equals`. Inputs of
   variable length are hashed to a fixed length first, because `FixedTimeEquals` returns at once when lengths differ.
4. Generated by the server. A credential the application issues is generated server-side from
   `RandomNumberGenerator`, with at least 256 bits of entropy, never chosen by the caller.
5. Shown once. The response that creates a credential returns it once, with `Cache-Control: no-store`. No read, list,
   update or preview returns it afterwards; they return its metadata (an identifier, a prefix for recognition, its
   creation and expiry times).
6. Stored so it cannot be read back. A credential the application only verifies is stored as a hash: a SHA-256 of a
   high-entropy random value, or a password-hashing function for a value a person chose. A secret the application must
   use itself, such as a key it signs with, is stored protected by a key held outside the store.
7. Rotated by create, then delete. A credential is rotated by creating a new one, letting its holder switch, and
   deleting the old one, so both are valid during the switch and no update changes a credential in place.
8. A bootstrap credential is configured. A first administrator or other bootstrap credential comes from a configured
   secret, never one generated at startup and printed to a log.

Secret buffers in memory are cleared after use
([ADR-0112](0112-binary-data-uses-spans-pooled-buffers-and-cleared-secrets.md)), and failure messages never quote one
([ADR-0111](0111-failures-carry-a-machine-readable-code.md)).

## Options considered

- Redact secrets in the logging pipeline. Kept as a backstop, rejected as the control: a redactor recognizes only the
  shapes it knows, and audit events, exceptions and stored payloads bypass it.
- Ordinary equality for secrets. Rejected: the timing difference is measurable over a network with enough samples.
- Return a credential on every read for convenience. Rejected: every read becomes a copy of the secret.
- Store generated credentials encrypted rather than hashed. Rejected for credentials the application only verifies:
  whoever holds the key reads them all, and nothing needs to.
- Never in diagnostics, constant-time comparison, shown once and stored hashed (chosen).

## Consequences

- A leaked log, trace, audit store or backup holds no usable credential.
- A holder who loses a credential cannot recover it; they create a new one and delete the old.
- Support and debugging work from identifiers and prefixes, never from the secret itself.
- Smell: a log message template with a parameter named `token`, `secret`, `password` or `key`; a `==` between two
  byte arrays or strings that hold a secret; an endpoint whose read model has the same shape as its create response.
