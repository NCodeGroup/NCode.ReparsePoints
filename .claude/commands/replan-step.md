## Work in the plan's worktree

Each plan lives in its own git worktree, so several Claude Code sessions can work on different plans on this machine at once. Before anything else, move this session to the plan:

1. Run `git rev-parse --show-toplevel`. If the path contains `/.claude/worktrees/` and has a `PLAN.md`, this session is in the plan's worktree: go on with the task.
2. Otherwise list the plan worktrees: run `git worktree list --porcelain`, keep each `worktree` path under `.claude/worktrees/` that has a `PLAN.md`, and read each plan's title from its first line.
3. Choose the plan, in this order: the worktree whose folder name the command's arguments give; else the only plan worktree; else, when there is no plan worktree, the `PLAN.md` in the current checkout, worked on where it is — a plan written without a worktree, such as in Copilot. Switch into a chosen worktree with the `EnterWorktree` tool and its `path`. With several plan worktrees and none named, list them with their titles and stop to ask which one. With no plan anywhere, stop and say so.

From here on, the plan's folder is the repository root: run every command there, Done-when commands included. In a worktree, never edit files or run git in the main checkout. When you delegate to a subagent, give it the folder's absolute path and tell it to work only there.

## Task

A step of `PLAN.md` came back from the executor: it escalated the step (marked `[?]` with an `- Escalation:` note) or failed it (marked `[!]`).

Step and details (may be empty): $ARGUMENTS
If that is empty, take the first step marked `[?]` or `[!]`.

You are the planner. Do the deep reasoning the executor must not do, then hand the step back for execution.

1. Read `PLAN.md`, the step and its Escalation note, and the current state of the files it touches — `git status` and `git diff` show any partial work.
2. If the step failed, run its Done-when command and read the failure. When the Context for the executor has a `- Prelude:` line, run its command first in the same PowerShell, dot-sourced, as the executor does: `$global:LASTEXITCODE = 0; try { . <prelude> } catch { $_; "prelude failed"; exit 2 }; if (-not $? -or $LASTEXITCODE) { "prelude failed"; exit 2 }; <the Done-when command>`, where `<prelude>` is that line's command. When it exits 2 and the output's last line, apart from any exit code your shell adds, is `prelude failed`, the check never ran, and the step isn't what failed: stop, show me the prelude's error, and say to fix the `- prelude:` line in the `## Landing` section of `AGENTS.md`, or the script it names, and the plan's `- Prelude:` line. Leave the step as it is.
3. Decide why it came back, with evidence: the step was ambiguous, too big, wrong about the code, missing context, needs a redesign, or is beyond the executor model.
4. Fix the plan rather than the code:
   - Ambiguous or wrong about the code: rewrite the step with exact files, symbols and behavior.
   - Too big: split it into smaller steps and renumber the steps after it.
   - Missing context: add it to Context for the executor or to the step.
   - Needs a redesign: make the design decision, record it under Decisions, and update every later step it affects.
   - Beyond the executor model: implement only this step yourself, run its Done-when command, and mark it `[x]`.
5. Keep or revert the partial work deliberately — say which, and run `git checkout -- <files>` when reverting.
6. Remove the step's `- Escalation:` line (its outcome now lives in the step or under Decisions) and change the heading marker back from `[?]` or `[!]` to `[ ]`, unless you completed the step.
7. When `PLAN.md` has an `Issue:` line under its title and this re-plan changed the Decisions or added or removed steps, post a short comment on each issue on that line yourself, one comment per issue: `Re-plan of step N` and two to five lines on what changed and why, without the full plan. On GitHub run `gh issue comment <number> --body-file <file>`, with the text in a temporary file outside the repository; on GitLab (`git remote get-url origin` contains `gitlab`) run `glab issue note <number> --message <text>`. When posting fails, say so in your report. A re-plan that only rewords or clarifies a step posts nothing. A session's own tooling can add agent attribution to what it posts, on GitHub or GitLab, whichever AI agent, assistant or model runs the session: a Claude Code cloud session appends a line `---` and then a footer line `_Generated by [Claude Code](https://claude.ai/code/…)_` to each pull request description, issue, comment and review-thread reply it creates, through `gh` and the GitHub MCP tools alike, and other agents, such as Copilot's coding agent, Codex, Cursor, Devin, Jules or GitLab Duo, can append a line of their own that says the text was generated, written or created with or by an AI tool, or a link to the agent's session or task, while `gh` or `glab` in a local session appends nothing. So straight after each command that creates or edits a pull request or merge request description, an issue, or a top-level comment or note, read back what was saved, from the repository it went to. On GitHub, use the GitHub MCP tools when the session has them, because in a Claude Code cloud session an edit through `gh` appends the footer again: `update_pull_request` with the new body for a pull request, `issue_write` with `method: update` and the new body for an issue, or `update_issue_comment` with the comment's id and the new body for a comment; without them, write the new body to a file and run `gh pr edit <number> --body-file <file>`, `gh issue edit <number> --body-file <file>` or `gh api -X PATCH "repos/<owner>/<repo>/issues/comments/<id>" -F body=@<file>`, with the same `--repo`. Then read it back once more; when the attribution is still there, the route appended it again: on GitHub, try the other route once, `gh` after the GitHub MCP tools or the GitHub MCP tools after `gh`, and when it is still there, or there is no other route, as on GitLab, leave it and list it in your report, and for a pull request or merge request description also say that the `Commit attribution` check may fail until a person deletes those lines. Two posts are exceptions. Never edit a `/review` comment, even when it came back with attribution: the `/review` request reads it back itself and deletes it when anything was appended, because NCode Review acts only on the comment as it was created, so an edited `/review` comment requests no review. A reply on a review thread is the other exception: on GitHub nothing a Claude Code cloud session can call edits one without its footer, so post each reply as these instructions say anyway, because every finding still gets its reply, and list the replies in your report as ones that may carry the footer; on GitLab, a reply on a discussion is a note, read back and edited as above with `discussions/<discussion id>/notes/<id>` in place of `notes/<id>`.
